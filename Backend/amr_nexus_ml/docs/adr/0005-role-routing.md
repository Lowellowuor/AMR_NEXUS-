# ADR-0005: Role-Based Alert Routing

- **Status:** Accepted
- **Date:** 2026-10-01

## Context

County stakeholder feedback (September 2026):

    "Distinguish between different levels of signals or gaps and determine
    who receives critical alerts versus high-priority alerts, supported by
    role-based access controls so that users only receive information
    relevant to their responsibilities."

    "User privileges need to be defined to guide who receives which kind
    of signal or alert."

Today the platform has `NotificationPreference` - per-user settings for
email severity, SMS severity, and desktop toggle. There is no way for an
administrator to say "clinicians should not receive SMS at all" or
"viewers only get desktop notifications at medium and above." Every user
configures their own thresholds, and nothing prevents a viewer from
subscribing to critical SMS.

For a Ministry deployment, alert fatigue is a real risk. A national
outbreak SMS goes to every clinician who has enabled SMS - including
those who should not receive it. And viewer accounts, meant for
read-only oversight, can currently be configured to receive every alert
on every channel.

## Decision

Introduce **role-based alert routing** as a first-class configuration and
implement it as a module under `src/modules/role_routing/`.

### Table: `role_routing`

| Column | Type | Notes |
|--------|------|-------|
| id | Integer PK | |
| role | String(20) | admin \| analyst \| clinician \| viewer |
| channel | String(20) | email \| sms \| desktop |
| min_severity | String(20) | critical \| high \| medium \| low |
| enabled | Boolean | default true |
| updated_by | Integer FK users.id | nullable |
| updated_at | DateTime | |

Unique constraint on `(role, channel)` - one rule per role/channel pair.

### Defaults seeded on first request

| Role | Email | SMS | Desktop |
|------|-------|-----|---------|
| admin | low | high | low |
| analyst | medium | critical | medium |
| clinician | high | critical | medium |
| viewer | medium | disabled | medium |

These are reasonable starting points, editable by an admin.

### Effective notification decision

An alert is sent to a user on a channel if **both** of these are true:

1. `role_routing` says the user's role is allowed to receive this severity
   on this channel (`enabled` is true AND `severity >= min_severity`).
2. `NotificationPreference` says the user has opted in for this channel
   at a severity level that includes the alert.

The two are AND-ed. Role routing is a ceiling; user preference is the
individual setting under that ceiling.

### API surface

| Method | Path | Purpose |
|--------|------|---------|
| GET    | /modules/role-routing                | List all rules |
| PATCH  | /modules/role-routing/{id}           | Update one (admin only) |
| POST   | /modules/role-routing/reset-defaults | Restore defaults (admin only) |

### Behaviour change

`notification_service.dispatch_alert` and `dispatch_prediction_alert`
now call a new `role_allows(role, channel, severity)` helper before
sending. If `role_allows` returns False, the channel is skipped for that
user even if their personal preference would have allowed it.

If no `role_routing` row exists for a `(role, channel)` pair, the
decision is **allow** (fail-open). This preserves current behaviour for
any roles not explicitly configured and avoids silent notification
outages on upgrade.

## Consequences

- Admins have a single place to govern who gets what.
- County pilot can be launched with strict defaults (viewers cannot
  receive SMS even if they ask).
- Existing per-user preferences remain meaningful within the new ceiling.
- This is the second migration generated by Alembic.
- The `notification_service.py` change touches an existing flow; a
  regression test is added to verify current behaviour is preserved when
  role routing is unset.

## Rejected alternatives

- **Only per-user preferences (current state).** Rejected: does not
  permit organisation-level policy, which is what a Ministry deployment
  requires.

- **Only role routing (drop per-user preferences).** Rejected: user
  preference is still the right place for individual opt-in within a
  role ceiling.

- **Config file, not DB.** Rejected: admins need to change routing
  without redeploying, and every change must be auditable.

- **Integrate in a follow-up PR.** Rejected: a routing table that does
  not affect dispatch is inert. Integration is the point of this PR.
